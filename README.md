# AIdeation

Eigenständiges Projekt mit Angular-Oberfläche und TypeScript-/Express-API: Sprints, Ideen, Aufträge, Bugs, Dokumentation, Statistik und automatisch arbeitende Agents. Unabhängig von den Anwendungen, die es betreut (z. B. Mainty).

## Schnellstart

```bash
git clone <repository-url> AIdeation/source && cd AIdeation/source
./start.sh          # Windows: start.cmd
```

Beim ersten Start führt ein Einrichtungs-Assistent im Browser durch Docker, Zugang und Worker; danach begrüßt dich
AIdeation mit dem Projekt-Assistenten und einer interaktiven Tour. Standard ist der **Worker im Container**: Auf
macOS, Linux und Windows braucht es dann nur Docker, `./start.sh` bzw. `start.cmd` startet AIdeation samt Worker und
Ausfall-Wächter. Ausführlich: [Installation](docs/installation.md).

## Starten (manuell)

1. Dienst + Datenbank: `docker compose up -d --build` → Oberfläche lokal `http://localhost:3100`, von aussen optional `https://<DEV_LOG_DOMAIN>` (siehe Sicherheit). Datenbank `127.0.0.1:5433`, eigenes Volume.
2. Worker im Container (Standard): `COMPOSE_PROFILES=worker` in der `.env` (mit Domain `https,worker`), einmal `npx tsx scripts/worker-compose.ts` (schreibt AIdeation-Ordner, Projektordner und Git-Zugänge in `docker-compose.override.yml`), dann `docker compose up -d --build`. Damit laufen die Dienste `worker` (einziger Dienst mit Docker-Socket) und `watchdog`. Log: `docker compose logs -f worker`. „AIdeation neu starten“ endet mit Exit-Code 75, Docker startet den Worker neu (siehe `docs/betrieb.md`, „Worker im Container“).
3. Worker auf dem Host (Alternative, Autostart per launchd): `./scripts/install-worker.sh` (Linux: `install-worker-linux.sh`, Windows: `install-worker.ps1`). Log: `~/Library/Logs/aideation-worker.log`. Ohne Autostart: `npm run worker`. Die Zugänge stehen in `~/.config/aideation/worker.env` (Rechte 600), nicht in der Plist (siehe `docs/betrieb.md`, „Worker auf dem Host: Dienste und Zugänge“). Nie beide Wege gleichzeitig.
4. Lokales Modell: Ollama (`DEV_LOG_OLLAMA_MODEL`, Standard `qwen3.5:9b`). Optional pro Rolle: `DEV_LOG_OLLAMA_MODEL_<ROLLE>` (z. B. `_DEVELOPER`) und Kontext `DEV_LOG_OLLAMA_CTX[_<ROLLE>]` (Standard 16384, Entwickler 32768); `DEV_LOG_OLLAMA_KEEP_ALIVE` (Standard `30m`) hält das Modell geladen. Ollama-Einstellungen (Modell dauerhaft geladen, Flash Attention, KV-Cache q8_0, ein Modell gleichzeitig) setzt `./scripts/configure-ollama.sh` und startet die Ollama-App neu. Bei Verbindungsfehlern wird bis zu zweimal mit wachsender Wartezeit wiederholt.

## Entwicklung

- Node.js 22.12 oder neuer (Projektversion: `.nvmrc`, Docker: `22.22.3`).
- `npm run dev` startet die API auf Port 3101 und läuft damit neben dem Compose-Stack (3100, 5433, 80, 443 gehören dem Live-Stack). Sie braucht eine eigene Datenbank, z. B. `DEV_LOG_DATABASE_URL=postgresql://devlog:<passwort>@127.0.0.1:5433/aideation_dev DEV_LOG_AUTH=off npm run dev`; die Datenbank wird beim Start angelegt. Auf `PORT=3100` oder die Live-Datenbank `aideation` startet die Dev-API nicht (`src/core/dev-environment.ts`).
- `npm run dev:ui` startet die Angular-Entwicklungsoberfläche auf Port 4200 und leitet `/api` und `/health` an die Dev-API auf Port 3101 weiter (`frontend/proxy.conf.json`), nie an den Live-Stack.
- `npm run build` baut die Angular-Oberfläche und kompiliert anschließend das Backend.
- `npm run test:unit` führt die Unit- und Integrationstests aus (Backend, Skripte, Frontend-Specs), ohne die Oberfläche zu bauen. Kein Test liest `dist/ui`.
- `npm test` ist der Komplettlauf: erst `build:ui`, dann `test:unit`.
- `npm run lint`, `npm run format:check` und `npm run typecheck` prüfen Stil und Typen. `typecheck` prüft auch die Test-Dateien (`tsconfig.test.json`, `frontend/tsconfig.spec.json`), denn `tsx` allein prüft keine Typen.
- `npm run test:e2e` startet die Oberflächentests (Playwright, eigene Datenbank `dev_log_e2e`; vorher `npm run build:ui`).
- CI (`.github/workflows/ci.yml`, nur Leserechte, bei Push auf `main` und bei Pull Requests): Job `check` (Lint, Format, Typen, `test:unit` gegen Postgres 17), Job `e2e` (Playwright gegen Postgres), Job `docker` (baut `dev-log`, `frontend`, `https`, das Review-Image und `aideation-agent`, prüft die Sandbox mit echtem Docker, startet danach `db`, `dev-log`, `frontend` sowie `worker` und `watchdog` mit Health-Prüfung und zufälligen, maskierten Zugangsdaten). Keine Secrets, kein Token in `.git/config` (`persist-credentials: false`), keine Coverage-Schwelle. Fehler stehen im Log (Playwright-Ausgabe, Container-Logs), Traces zusätzlich als Artefakt. `.dockerignore` hält `.env*`, Schlüssel, Sicherungen und Testergebnisse aus den Images heraus.

### Sicherheit

Login ist standardmäßig an (`DEV_LOG_USERNAME`, `DEV_LOG_PASSWORD` ≥ 16 Zeichen in `.env`). Die Oberfläche (`aideation_frontend_angular`, nginx) ist nur an `127.0.0.1:3100` gebunden und leitet `/api` an das Backend (`aideation_backend_nodejs`, Nicht-Root, ohne eigenen Port nach aussen) weiter. Von aussen geht der Zugriff ausschließlich über HTTPS: Der Dienst `https` (Caddy, `deploy/Caddyfile`) lauscht auf 80/443, holt das Zertifikat für `DEV_LOG_DOMAIN` automatisch bei Let's Encrypt und leitet an die Oberfläche weiter (Router: Port 443 auf diesen Rechner weiterleiten). AIdeation übernimmt Protokoll und Client-IP vom Proxy (`DEV_LOG_TRUST_PROXY`). API und Oberfläche setzen dieselben Security-Header (CSP; nginx: `deploy/frontend/security-headers.conf`), weist schreibende Cross-Origin-Anfragen ab und bremst Anmeldeversuche: Nach 10 Fehlversuchen je Quelle und Konto wächst die Wartezeit ab 1 Minute bis höchstens 15 Minuten. Ohne Container (`npm start`, `npm run dev`) lauscht der Server nur auf `127.0.0.1`; `DEV_LOG_HOST` überschreibt das (im Container `0.0.0.0`). API-Pfade unterscheiden Groß-/Kleinschreibung, Anmeldung, Rollen und Mandantenprüfung hängen am Router unter `/api`.

Anmeldung über die Login-Seite (Sitzungs-Cookie, 30 Tage). Jede Sitzung ist an das Passwort gebunden (Spalte `auth_sessions.credential_version`): Ein neues Benutzerpasswort beendet alle Sitzungen dieses Benutzers, ein neues `DEV_LOG_PASSWORD` in der `.env` beim nächsten Start alle Sitzungen des Systemadministrators. Abgelaufene und ungültige Sitzungen löscht der Dienst beim Start und danach stündlich. Unter Einstellungen → Sicherheit lässt sich die Zwei-Faktor-Anmeldung mit einer Authenticator-App einrichten; danach gilt Basic Auth (für Skripte) nicht mehr. Einrichten, Ersetzen und Ausschalten verlangen das aktuelle Passwort und, wenn der zweite Faktor schon aktiv ist, einen aktuellen Code. Die TOTP-Schlüssel liegen mit `DEV_LOG_SECRET_KEY` verschlüsselt in der Datenbank. Ohne diesen Schlüssel lässt sich kein zweiter Faktor einrichten, und sind schon Schlüssel gespeichert, startet der Dienst nicht. Code verloren: Für den Systemadministrator (Anmeldung aus der `.env`) liegt der Schlüssel in `app_settings.auth_totp_secret` – `docker compose exec db psql -U devlog aideation -c "DELETE FROM app_settings WHERE key IN ('auth_totp_secret', 'auth_totp_pending')"` und `docker compose restart dev-log` (der Dienst liest ihn nur beim Start). Für benannte Benutzer liegt er in `users.totp_secret`: ein Administrator setzt ihn unter Einstellungen → Alle Projekte → Benutzer & Rollen zurück (`POST /api/users/<id>/totp/reset`), ohne Administrator-Zugang `docker compose exec db psql -U devlog aideation -c "UPDATE users SET totp_secret = NULL, totp_pending = NULL WHERE lower(username) = lower('<name>')"`; ein Neustart ist dafür nicht nötig.

### Betrieb

- **App & Push:** AIdeation ist als App installierbar (Manifest, Service Worker). Unter Einstellungen → App & Benachrichtigungen pro Gerät Push einschalten (iPhone: erst „Zum Home-Bildschirm“). Meldungen: Auftrag erledigt/blockiert, Antwort/Rückfrage des Assistenten, Ausfall.
- **Backups:** Dienst `backup` schreibt etwa täglich `backups/aideation-*.dump` (neuer Dump, wenn der letzte über 23 Stunden alt ist; geprüft stündlich) (14 Tage, `DEV_LOG_BACKUP_KEEP_DAYS`; die neuesten 7 bleiben immer, `DEV_LOG_BACKUP_MIN_KEEP`; rotiert wird nur nach erfolgreichem Dump). Wiederherstellen nur mit `bash scripts/restore.sh backups/<datei>.dump`. Das Skript prüft die Datei und stoppt API, Oberfläche, den Backup-Dienst sowie Worker und Wächter auf dem Host (Compose-Worker und -Wächter vorher selbst stoppen, siehe [Betrieb](docs/betrieb.md#wiederherstellen)). Dann spielt es das Backup mit `--exit-on-error --single-transaction` in eine neue Datenbank ein, testet `DEV_LOG_SECRET_KEY` per Entschlüsselung, tauscht erst danach die Datenbank aus und startet alles wieder. Die bisherige Datenbank bleibt als `aideation_vor_restore_<zeit>` erhalten. **Nötig ist derselbe `DEV_LOG_SECRET_KEY` wie beim Backup** (in `.env`, `worker.env` und `watchdog.env`), sonst sind Projektzugänge, Zwei-Faktor-Schlüssel und der private Push-Schlüssel (VAPID) nicht lesbar. Verschlüsselt sind im Dump nur diese drei Arten von Werten; alles andere (Aufträge, Doku, Agent-Ausgaben, Benutzer mit Passwort-Hashes, Push-Abos) steht lesbar darin. Bewahre den Schlüssel deshalb getrennt von den Backups auf, z. B. im Passwortmanager – liegt er mit im Backup, schützt die Verschlüsselung nichts. Lege außerdem regelmäßig eine **zweite Kopie von `backups/` außer Haus** ab, z. B. auf einem externen Laufwerk an einem anderen Ort oder verschlüsselt in der Cloud. `backup_check` prüft alle 6 h das neueste Backup mit `pg_restore --list` (Postgres-Client ab 17 auf dem Worker-Rechner oder `DEV_LOG_PG_RESTORE`; das Worker-Image bringt ihn mit). `restore_probe` spielt es wöchentlich in einen Wegwerf-Container ein (`bash scripts/restore.sh --probe …`, Port 5439). Details: [Restore](docs/auftraege/restore-skript-und-probe-2026-10-27.md).
- **Wächter:** im Container der Dienst `watchdog` (Standard), auf dem Host `./scripts/install-watchdog.sh`; er prüft alle zwei Minuten Dienst, HTTPS, Datenbank, Worker, Backup-Alter und Speicherplatz und meldet Probleme per Push (Log auf dem Host: `~/Library/Logs/aideation-watchdog.log`, im Container `docker compose logs watchdog`). Fällt der ganze Rechner oder die Internetleitung aus, kann er nichts melden – dafür einen externen Monitor auf `https://<DEV_LOG_DOMAIN>/health` setzen.
- **Produktions-Rückkanal:** Unter Einstellungen → Betrieb je Projekt Health-URL (nur http(s) auf localhost, LAN oder eigener Domain: `DEV_LOG_DOMAIN`, `DEV_LOG_OWN_DOMAINS`), Compose-Dienste für den Log-Scan, Ausschlussmuster, Aufbewahrung (Standard 30 Tage) und das Ingest-Token (nur der Hash wird gespeichert). Der Worker prüft die Health-URL alle 2 Minuten (zwei Fehlschläge in Folge = kritischer Bug „Anwendung nicht erreichbar“ und Push, Erholung = Entwarnung) und liest alle 15 Minuten sowie nach jedem Deploy `docker compose logs --since 15m --no-color`. Die Anwendung kann Fehler selbst an `POST /api/ingest/<projekt>/<token>` melden (ohne Login, 16 KB, Rate-Limit). Gleiche Fehler werden über einen Fingerabdruck gebündelt, maskiert und erst ab drei Vorkommen innerhalb von 24 Stunden als Bug mit Quelle „Betrieb“ erfasst (Ausfälle wie ein Health-Ausfall sofort); ein behobener Bug wird bei erneutem Auftreten als Regression geöffnet. Snippets für Browser und Node: Dokumentation → „Betrieb: Fehler an AIdeation melden“.
- **Oberflächentests:** `npm run test:e2e` (Playwright, Desktop und Handy) startet AIdeation auf einer eigenen Datenbank `dev_log_e2e`; einmalig `npx playwright install chromium`.

Wichtig: Wer sich anmelden kann, kann über Agent-, Test- und Deploy-Befehle beliebige Befehle auf dem Rechner des Workers ausführen. Deshalb ein starkes Passwort verwenden und AIdeation nie per HTTP ins Netz stellen.

**Grenzen der Agent-Rechte:** Die Grenze zum Rechner ist der Arbeitscontainer je Projekt (`DEV_LOG_AGENT_SANDBOX`, Standard `workbench` beim Worker auf dem Host; der Compose-Dienst `worker` nutzt fest `docker`, siehe [Betrieb](docs/betrieb.md#arbeitscontainer-für-agents)): ein dauerhafter Compose-Stapel mit eigenem Docker (`docker:29-dind-rootless`, nicht privilegiert) und den Testdiensten aus `.aideation/workbench.json`. Darin dürfen Agents bauen, testen und Container starten, ohne den Rechner oder dessen Docker zu berühren; lesende Rollen laufen in kurzlebigen Containern (Label `aideation.run`, Modus `docker`). Das gilt für alle Rollen, den Chat, die Routinen, den Visionär, die Problemanalyse und die System-Agents. Auch das Projekttests-Gate, `npm run test:full` und die Abdeckungsmessung laufen dort. Eingebunden ist nur der Worktree, für lesende Rollen nur `:ro`. Nach aussen geht es nur über einen Egress-Proxy zur Anthropic-API, zur npm-Registry, zu Docker Hub und zu Ollama. LAN und AIdeation-Datenbank sind gesperrt. Der Host führt damit keinen Code mehr aus, den Agents geschrieben haben. Die Werkzeugregeln und der Wächter (Projektordner, gesperrte Dateien, erlaubte Befehle) sind die zweite Linie: Sie schützen vor Fehlgriffen des Modells, auch im Container. `DEV_LOG_AGENT_SANDBOX=off` ist nur ein ausdrücklicher Notfallmodus, und das Worker-Badge warnt dann. In diesem Modus laufen Agents, Tests und npm-Skripte wieder mit den Rechten des Workers auf dem Host. Agents dürfen Pakete nur mit `npm install|ci --ignore-scripts` installieren. Die Projektvorlagen des Assistenten laufen ebenfalls ohne Install-Skripte (`--ignore-scripts` und `npm_config_ignore_scripts=true`) und mit fest eingetragenen Generator-Versionen (`GENERATORS` in `src/setup/templates.ts`). Den Generator selbst führt der Worker trotzdem auf dem Host aus. Für die Projekt-Datenbank einen eigenen Benutzer ohne `DROP`-/Superuser-Rechte hinterlegen.

### Struktur

- `src/api/` Express-Routen, `src/core/` Hilfen (Validierung, Befehle, Sperren), `src/db/` Schema und Zugriff, `src/agent/` Ollama-Agent, Chat und Rollen, `src/runner/` Sprint-Runner, Worker, Tests und Git.
- `frontend/src/app/` Shell (`app.component`), `core/` (Store, API, Modelle), `shared/` (Pipes, Hilfen, kleine Komponenten), `features/<bereich>/` je ein Bereich der Oberfläche.

## Projekt anlegen

In der Oberfläche ein Projekt anlegen und unter **Projekteinstellungen** angeben:

- **Projektordner**: absoluter Pfad. Dort lesen und schreiben die Agents, dort laufen die Tests und der Git-Sync.
- **Testbefehle** (optional): ein Befehl pro Zeile, Standard `npm run build` + `npm test`.
- **GitHub-Repository** (optional): `git@github.com:user/repo.git`, Zugang über SSH-Key, nie Zugangsdaten in der URL.
- **GitHub-Brücke** (optional, Standard aus): Issues mit Label `idea`/`bug` übernehmen und Status zurückmelden, wahlweise Sprint-Abschluss als Pull Request mit CI-Ampel. Braucht `gh auth login` des Worker-Benutzers bzw. im Worker-Container ein Token aus `DEV_LOG_WORKER_GITHUB_TOKEN_FILE` (siehe `docs/workflows.md`).

Der Worker bedient jedes registrierte Projekt in dessen Ordner. Fehlt der Ordner, zeigt das Worker-Badge den Fehler.

## Ablauf

- Neue **Ideen** formuliert der Auftragsautor automatisch zu Aufträgen im Backlog aus; per „Erneut anfragen“ mit Änderungswunsch überarbeitbar.
- **Sprints** werden manuell zugewiesen und gestartet. Nur Aufträge aktiver Sprints werden bearbeitet.
- **Workflow** je Auftrag: Pre-Task → While-Task → After-Task (Bug-Wächter, Entwickler, Tester, Dokumentierer, Handbuch-Autor). Erfolg → `done`, Fehlschlag → `blocked` plus automatischer Bug.
- Der Dashboard-Assistent übernimmt auch die Problemlösung: Er darf Fehler im Projektordner untersuchen und gezielt beheben; Dateien außerhalb des Projektordners, `.env`, Schlüssel, `node_modules` und `.git` bleiben gesperrt. Dienste verwaltet er nicht per Shell, sondern über feste Worker-Aktionen: `services.status`, `services.logs` (mit Zeilenlimit und Zeitraum), `services.restart`, `services.up` (optional mit Build) und `services.stop`. Der Worker prüft jede Anfrage (Projektordner, Compose-Datei im Projekt, bekannter Dienst, Rolle), führt `docker compose` unter der Projektsperre selbst aus und gibt das maskierte Ergebnis zurück. Mit der Claude-CLI fordert der Assistent eine Aktion mit einer Zeile `@@SERVICES: services.restart <dienst>` an, das Ergebnis erscheint im Chat. Das lokale Modell nutzt das Werkzeug `service_action`. `docker`, `docker compose` und `launchctl` sind für alle Agents gesperrt; kein Agent braucht den Docker-Socket. Umgebungen setzt er weiter selbst auf (`git clone` per https/ssh in einen Unterordner des Projektordners, `git pull`, `npm install`); Pfade außerhalb des Projekts sind nicht erlaubt. Der Entwickler-Agent schreibt weiterhin mit Backups in `.dev-log-backups/`.
- Beim Abschluss eines Sprints: Bericht (umgesetzt / fehlt / Probleme) und Git-Sicherung (Commit `Sprint: <Name>`, Tag, Push).
- Eigene Agent-Befehle (z. B. `claude -p`) pro Agent oder global über `DEV_LOG_AGENT_COMMAND`; sonst der eingebaute Ollama-Agent.
- Manuelle Läufe: `npm run runner -- --project <slug> --cwd <Pfad>` bzw. `npm run test-agent -- --project <slug>`.

## Konfiguration

`DEV_LOG_DATABASE_URL`, `DEV_LOG_ADMIN_DATABASE_URL`, `DEV_LOG_TIMEZONE` (IANA-Zeitzone für Tagesgrenzen von Budget-Tag und Burndown, Standard `Europe/Zurich`; die Datenbank bleibt in UTC), `DEV_LOG_AUTH` (`off` = kein Login, nur in vertrauenswürdigen Netzen), `DEV_LOG_PROJECT_ROOTS` (Doppelpunkt-getrennte Ordner, unter denen Projektordner liegen müssen), `DEV_LOG_USERNAME` / `DEV_LOG_PASSWORD`, `DEV_LOG_AGENT_COMMAND`, `DEV_LOG_MAX_TURNS`, `DEV_LOG_TEST_COMMANDS` (Fallback, JSON), `DEV_LOG_OLLAMA_URL`, `DEV_LOG_REVIEW_DATABASE_URL` (nur Worker: eigener DB-User ohne Superuser-Rechte für Review-Container, angelegt mit `scripts/setup-review-db.sh`; ohne ihn startet kein Review-Container für Projekte ohne eigene Datenbank, siehe `docs/laufzeit.md`), `DEV_LOG_SECRET_KEY` (≥ 16 Zeichen: verschlüsselt die Datenbank-Zugänge der Projekte, die TOTP-Schlüssel und den privaten VAPID-Schlüssel für Push mit AES-256-GCM, damit sie auch in Backups nicht im Klartext stehen; beim Start werden bestehende Klartext-Werte umgestellt. Sind TOTP- oder VAPID-Schlüssel gespeichert und fehlt der Schlüssel, startet der Dienst nicht. Derselbe Wert muss in `.env` für den Container und beim Installieren von Worker und Wächter gesetzt sein, z. B. `DEV_LOG_SECRET_KEY=… ./scripts/install-worker.sh` und `… ./scripts/install-watchdog.sh`; geht er verloren, müssen die Zugänge neu eingetragen, der zweite Faktor neu eingerichtet und Push auf den Geräten neu aktiviert werden).

Datenmodell: [docs/erm.md](docs/erm.md).

## Git im Sprint

Jeder Sprint arbeitet auf einem eigenen Branch `sprint/<name>`. Nach jedem erfolgreich erledigten Sprint-Auftrag erstellt der Worker dort einen lokalen Commit (Conventional Commits, z. B. `feat(Sprint 1): Titel`, Bugs als `fix`); Änderungen fehlgeschlagener Aufträge bleiben als WIP-Commit auf ihrem Auftrags-Branch statt im Sprint-Branch. Die Sprint-Sicherung pusht nur bei grünen Projekttests; beim Abschluss wird nach `main` gemergt, erneut getestet, gepusht und getaggt. `.env`, `.dev-log/`, Agent-Sicherungen und Dateien, die nach Zugangsdaten aussehen, werden nie committet. Details: [Workflows](docs/workflows.md#6-git-im-sprint).

Dokumentation: [Agents und Rechte](docs/agents-und-rechte.md), [Agent-Tests](docs/agent-tests.md), [Workflows](docs/workflows.md), [Seiten-Vorlage](docs/seiten-vorlage.md) (wie eine Seite gebaut und geprüft wird).

Im Dashboard zeigt Dokumentation → Marketing → „Agents, Aufgaben und Rechte“ (`#docs/marketing/agent-permissions`, nur mit dem Recht „Dokumentation bearbeiten“) die Rollen aus `agents.role` mit Phase, Aufgabe, Datei- und Befehlsrechten, den Ablauf als Diagramm und die Sicherheitsgrenzen. Die Inhalte stehen statisch in `frontend/src/app/features/docs/marketing/agent-permissions.ts` und stammen aus [Agents und Rechte](docs/agents-und-rechte.md), Abschnitt 3. Ändert sich dort die Tabelle „Workflow-Agents“, schlägt `npm test` fehl, bis die Seite nachgezogen ist.
